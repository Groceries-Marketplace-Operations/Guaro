01
Flujo completo
Del archivo al resultado de la API.

        
    
            
  1. CargarSe elige la marca y se lee un archivo local o de su cuenta SFTP de promociones.
    2. 
          
  2. ValidarSe revisan columnas, tipos, fechas, identificadores, mecánicas y filas duplicadas.
    3. 
          
  3. SeleccionarSe eligen las promociones y una, varias o todas las tiendas de la marca.
    4. 
          
  4. TransformarOpcionalmente se agrupan promociones y se cambian Activity ID o UPC.
    5. 
          
  5. RevisarSe genera el JSON exacto y se divide en lotes válidos antes de habilitar el envío.
    6. 
          
  6. Enviar y consultarCada tienda usa su token; consulta los Task IDs en la sección Seguimiento.
    7. 
        

        
La vista previa es obligatoria. Cambiar la selección, los identificadores o el destino requiere generar una nueva antes de enviar.

      


      

        
02
Plantilla de entrada
Formatos, encabezados y una fila por producto.

        

          

            
Formatos admitidos

            
    
              
  • .csv, .txt, .tsv, .xlsx y .xls.
    • 
              
  • Máximo 12 MB desde el navegador.
    • 
              
  • En CSV, TXT y TSV el encabezado es opcional. Sus nombres no son obligatorios: se usa la posición siempre que existan exactamente 14 columnas en el orden estándar de Soriana.
    • 
              
  • En CSV se detecta |, coma, punto y coma o tabulación.
    • 
              
  • En Excel debe existir una sola hoja utilizable y las celdas no pueden contener fórmulas.
    • 
            

          

          

            
Cómo se agrupan las filas

            
Cada fila representa un UPC dentro de una promoción. Las filas con el mismo shopid y activityid se convierten en una sola promoción con varios elementos en item_activity_list.

          

        

        
Orden estándar de 14 columnas (con o sin encabezado)

        
shopid,activityid,activityname,startdate,enddate,activitytype,sku,discountamount,discountpercentage,mxn_n,mxn_m,BXGY_X,BXGY_Y,activityaction

        
Este es el mismo número y orden de columnas utilizado por los archivos SFTP de Soriana. Si existe encabezado pero sus nombres son distintos o incompletos, se usa el orden posicional. No se reordenan, agregan ni omiten valores.

03
Tipos de promoción
Solo se admiten los tipos 2, 4 y 8.

        

          

            2
            
Descuento porcentual

            
Usa discountpercentage o DiscPercentage.

            
  • Debe ser un entero entre 5 y 99.
  • Los valores de 1 a 4 y 100 son rechazados por DiDi.
  • Los campos de tipos 4 y 8 deben quedar vacíos.

          

          

            4
            
Compra N, recibe M

            
Usa mxn_n/BuyNum y mxn_m/GetNum.

            
  • Ambos son enteros positivos.
  • buy_num debe ser menor que get_num.
  • Ejemplo 3×2: BuyNum=2 y GetNum=3.

          

          

            8
            
Cantidad a precio fijo

            
Usa BXGY_X y BXGY_Y o final_discounted_price.

            
  • BXGY_X es un entero positivo.
  • El precio se interpreta en pesos y se convierte exactamente a centavos.
  • Se agrega child_type: 5.

          

        

        
Regla confirmada por la API. DiDi devuelve errno: 10001 y el mensaje 【discount_perc】 must be between 5 and 99 integer cuando algún producto queda fuera de ese rango. La herramienta permite omitir explícitamente esos productos antes de generar el JSON.

        
No se redondean precios. Para pesos se admiten como máximo dos decimales. Un valor con fracciones menores a un centavo se rechaza.

      


      

        
04
Reglas y validaciones
Qué debe cumplirse para generar la vista previa.

        

          

            
Identificadores y fechas

            
    
              
  • Guarda shopid, activityid y sku como texto para conservar ceros e IDs largos.
    • 
              
  • No se acepta notación científica. Excel pierde precisión después de 15 dígitos si el valor no se guardó como texto.
    • 
              
  • Las fechas usan exactamente YYYY-MM-DD HH:mm:ss, sin zona horaria ni milisegundos.
    • 
              
  • La fecha inicial no puede ser posterior a la fecha final.
    • 
              
  • Los Activity ID o UPC modificados deben contener de 1 a 64 dígitos.
    • 
              
  • En todo JSON de creación, activity_name comienza con el Activity ID final: <ActivityID> · <nombre>.
    • 
            

          

          

            
Consistencia de promociones

            
    
              
  • El archivo de creación usa activityaction=1. En la interfaz puedes elegir 1 para crear o actualizar, y 2 para detener.
    • 
              
  • Si un UPC se repite dentro del mismo shopid + activityid, debes elegir explícitamente qué fila y mecánica conservar antes de generar la vista previa.
    • 
              
  • Las filas con descuento de 0% requieren elegir entre conservarlas exactamente como están u omitirlas del JSON.
    • 
              
  • Los productos con discount_perc de 1 a 4 o igual a 100 no se envían salvo que el usuario elija omitirlos. La cantidad, los porcentajes y las filas omitidas quedan registrados en la auditoría.
    • 
              
  • Todas las filas de una promoción deben coincidir en tipo, acción y vigencia. Si un mismo Activity ID contiene nombres distintos, se usa el nombre común Promoción <ActivityID> y se muestra una advertencia.
    • 
              
  • Solo deben llenarse los campos numéricos correspondientes al tipo elegido.
    • 
              
  • Un UPC puede aparecer en promociones distintas; se conserva y se muestra como advertencia.
    • 
            

          

        

        

          
Acción 1 · Crear o actualizarEnvía todos los datos de la plantilla para crear o actualizar la promoción.

          
Acción 2 · DetenerEnvía únicamente action y el Activity ID original.

          
Acciones mixtasCada promoción elige su acción; el mismo promo_list puede crear una actividad y detener otra.

          
ConservarMantiene cada Activity ID del archivo.

          
ManualRequiere un único resultado final y un ID nuevo que no exista en el archivo.

          
AleatorioGenera un ID numérico único y de longitud equivalente para cada promoción.

          
Cambiar UPCAplica el reemplazo en todos los destinos y bloquea colisiones dentro de una promoción.

        

      


      

        
05
Agrupación de promociones
Cuándo se pueden consolidar varias actividades.

        
Al activar Agrupar coincidencias, solo se consolidan promociones que tengan exactamente la misma tienda origen, acción, tipo, subtipo, fecha inicial y fecha final.

        

          
CoincidenSe unen los productos
Los UPC idénticos se conservan una sola vez cuando su mecánica también es idéntica.

          
Nuevo eventoActivity ID nuevo
Todo grupo de dos o más promociones recibe un ID numérico único para no sobrescribir las actividades originales.

          
ConflictoSe bloquea la agrupación
Si el mismo UPC tiene mecánicas diferentes, se detiene la vista previa y se muestra el conflicto.

        

      


      

        
06
Destino, envío y Task ID
Cómo llega cada solicitud a producción.

        

          

            
Destino y autenticación

            
    
              
  • El auth_token determina la tienda que recibe la promoción.
    • 
              
  • app_item_id_type=0 interpreta el producto como app_item_id; 1 lo interpreta como UPC.
    • 
              
  • Los perfiles de marca aplican valores iniciales. Soriana usa UPC de manera predeterminada y los ajustes se conservan en este navegador.
    • 
              
  • Cada tienda usa su propio token; un mismo token no puede reutilizarse entre destinos.
    • 
              
  • Para varias tiendas, Tequila genera los tokens sin mostrarlos en la interfaz.
    • 
              
  • “Toda la marca” crea una solicitud independiente y autenticada para cada tienda.
    • 
            

          

          

            
Lotes y resultado

            
    
              
  • Cada solicitud admite hasta 499 Activity IDs y 5,999 productos en total.
    • 
              
  • El límite de productos se aplica a toda la solicitud, no a cada promoción. Si una promoción no cabe completa, continúa con el mismo Activity ID en el siguiente lote.
    • 
              
  • Un rechazo de una tienda no detiene las tiendas restantes.
    • 
              
  • Los resultados se clasifican como aceptados, rechazados o desconocidos.
    • 
              
  • Al generar el JSON se guarda una auditoría local con el archivo y su hash, la selección, las tiendas, los cuerpos JSON exactos y un inventario de Activity IDs para revisar o detener. Después del envío se agregan las respuestas y los Task IDs, sin guardar tokens.
    • 
            

          

        

        

          
1
DiDi recibe el POST y responde si la solicitud fue aceptada para procesarse.

          
→

          
2
Se conserva el Task ID exacto como texto para evitar redondeo de identificadores de 64 bits.

          
→

          
3
Se consulta con la misma tienda porque el Task ID debe validarse con su token correspondiente. En envíos múltiples se consultan todos en paralelo y se filtran en una tabla.

        

        
Progreso real y pantalla ligera. La consulta muestra primero los lotes de credenciales y después los Task IDs terminados, el porcentaje y el tiempo estimado. La tabla presenta 50 filas por página y descarga el JSON original únicamente cuando abres “Ver JSON”.

        
Aceptado no significa aplicado. La respuesta inicial confirma que DiDi recibió el lote; la consulta del Task ID confirma su procesamiento final.

      


      

        
07
Diagnóstico automático
Muestreo preventivo, sin modificar producción.

        
La herramienta agrupa las cuentas SFTP por marca, elige el archivo cargable más reciente de una tienda y lo procesa con el mismo convertidor que genera los JSON. Un resultado sano significa que esa muestra no activó las reglas; no certifica todos los archivos de la marca.

        

          
CríticoEl archivo no cumple el estándar o contiene una decisión peligrosa, como 0%, UPC duplicado incompatible o precio de un centavo.

          
AdvertenciaEl valor es técnicamente válido, pero está fuera de los umbrales normales y requiere revisión humana.

          
InformativoFormato poco común que puede ser correcto según el catálogo de la marca.

        

        
Es una muestra. Se revisa una tienda por marca para detectar señales rápidamente; el diagnóstico no sustituye una validación completa de todos los archivos.

      


      

        
08
Operación SFTP por tienda
Edición opcional y envío masivo con una sola vista previa.

        
    
          
  1. Elegir cuentaLa cuenta fija la marca, las tiendas disponibles, el perfil de productos y las credenciales utilizadas.
    2. 
          
  2. Elegir alcance“Más reciente” toma un solo archivo por shopid; “específico” procesa únicamente el archivo seleccionado.
    3. 
          
  3. Filtrar mecánicaSolo se preparan los tipos 2, 4 u 8 seleccionados. La tabla indica su nombre, promociones y productos.
    4. 
          
  4. Aplicar reglasPara tipo 2 se omiten 0% y porcentajes fuera de 5–99. Los UPC duplicados idénticos se consolidan; una mecánica contradictoria bloquea esa tienda.
    5. 
          
  5. Asignar IDLas promociones con el mismo tipo y vigencia se agrupan. El Activity ID indicado se aplica únicamente cuando el archivo produce una sola actividad final.
    6. 
          
  6. Editar con respaldoSi se cambia la vigencia, se compara la huella del original, se crea un respaldo en .promo-manager-backups, se sube a una ruta temporal y se verifica antes de reemplazar.
    7. 
          
  7. Enviar por tiendaCada archivo se asocia con su tienda por App Shop ID y cada request usa el token propio de esa tienda. El fallo de una tienda no detiene las restantes.
    8. 
        

        
La preparación no modifica nada. La edición SFTP y el envío a la API solo comienzan después de marcar la confirmación y pulsar “Ejecutar operación”. Si el archivo cambió después de la vista previa, no se sobrescribe.
